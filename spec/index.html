PlateSmith — Public Feature Specification

Version: 1.1 (launch) · Published: August 2026 · Author: Mert Kalfa

This is the full feature specification for PlateSmith, published openly so that anyone interested — whether a developer, a lifter with access to AI coding tools, or just someone curious about how the app works — can see exactly what it does, how it's structured, and why each decision was made. If you want to build something similar, this is enough to do it.

PlateSmith was designed by me and coded by Claude (Anthropic's AI). I did the spec, the domain decisions, the UI review, and the gym testing. Claude wrote every line of Dart. This document is the spec I gave it.

1. What it is

A strength-training logger for Android (Flutter/Dart), optimised for speed of entry between sets and honest progression tracking across training blocks. Local-only, offline-first, single user.

What it replaces: Strong, Hevy, Boostcamp — each of which misses at least one of: proper warmup automation, per-exercise progression schemes with form gating, pinned technique notes, and training-block analytics measured in cycles rather than calendar weeks.

What it is not: A social app, a coaching platform, a nutrition tracker, or a cardio logger. No accounts, no cloud, no subscriptions.

2. Domain model

TrainingBlock ──< BlockPhase >── Program ──< ProgramDay ──< ProgramExercise
                                                                │
Exercise (library) ─────────────────────────────────────────────┘

Session (a performed ProgramDay) ──< SessionExercise ──< SetEntry

Exercise — A library entity (e.g., "Low-Bar Back Squat"). Owns: name, equipment type, per-exercise bar weight, display unit (kg or lb), plate inventory, loading step, default increment, warmup rule, rest timer default, pinned note (technique cues), measurement metric (reps or time), muscle group (chest / back / shoulders / arms / legs / core, or uncategorized). Follows the movement across programs.

Program — A named collection of up to 7 days (Day 1 … Day 7). Days form a rotating queue, not weekday-bound: you pick any day, and the app suggests the next unperformed one.

ProgramExercise — An exercise's slot inside a day: target set count, rep range, progression scheme, increment override, warmup rule override, target RPE.

TrainingBlock — An ordered sequence of phases, e.g., "6 cycles of Upper/Lower → 4 cycles of Full Body." Analytics roll up per block. Duration is measured in cycles, not calendar weeks.

Cycle — One full pass through a Program's days. The unit of block progress. A cycle advances only when every day is completed or explicitly skipped. Nothing auto-advances.

Session — An actual performed workout. Records: start/finish time, elapsed time, bodyweight (optional, prompted at finish), notes.

SetEntry — One set: type, weight, reps (or duration for timed exercises), RPE, technique flag, completion timestamp.

2.1 Cycles, not calendar weeks

Block progress is measured in cycles — one full rotation through the program's days — because training doesn't respect calendar boundaries. If you do Days 1–3 in one week and Day 4 the following Monday, that is still cycle 1.

The header reads "Cycle 1 of 12." Never "week." Skipping is a first-class action: skipped days are recorded (status: skipped) so adherence stats stay honest and the cycle can close. Repeating a day within a cycle is allowed and does not advance the counter.

2.2 Set types

Type Visual Counts toward volume Drives progression
warmup grey / outlined No No
work accent / solid Yes Yes
dropset amber / indented Yes (flagged) No
backoff blue-grey Yes No
AMRAP accent + badge Yes Yes

Type is freely editable per set (tap the # cell to change). Sets can be inserted anywhere and reordered.

2.3 Timed exercises

Exercises can be measured by reps (default) or time. Timed exercises (planks, carries) log a duration in seconds instead of reps. The set table shows "0:45" instead of "8 reps." A dedicated set timer dialog handles the countdown with a 5-second lead-in, voice cues, and countdown pips.

3. The session screen — the core UI

The screen you look at for 60–90 minutes. Everything else is secondary.

3.1 Whole-session visibility (hard requirement)

Starting a day shows the entire session at once — every exercise, every planned set, every prescribed weight and rep target — not a wizard that reveals one exercise at a time. You should be able to see the whole workout before you touch the first bar, and scroll back to a finished exercise to add a set or fix a number.

All exercise cards render in a single scrolling list, in program order. Cards are collapsible: the current exercise is expanded, completed ones auto-collapse to a one-line summary ("Squat · 3×6 @ 120 kg · RPE 8") but expand on tap.

3.2 Sticky session header

Pinned at the top: day name, set progress counter ("12/18 sets"), cycle info, elapsed workout timer, and an exercise progress bar showing completion at a glance.

3.4 Interactions

  • Tap a cell → numeric editor tuned to the field. Weight: step buttons matching loading step + free entry, with plate math shown. Reps: integer stepper + chip row. RPE: 6.0–10.0 in 0.5 steps, chip-only (no free entry — deliberate constraint). Duration: seconds stepper + chip row.
  • Swipe right on a row → duplicate set below.
  • Swipe left on a row → delete set.
  • Tap # cell → set type picker (warmup / work / drop / backoff / AMRAP).
  • Tap form cell → cycles through: unset → good (👍) → needs work (👀) → unset.
  • Check ✓ → marks set complete, auto-starts rest timer.
  • Drag handle → reorder exercises within the live session.

3.5 Pre-filling

Rows are pre-filled from the last session's performance of the same program exercise, including warmup rows and set count. A session with no changes is pure check-tapping.

3.6 Notes (three kinds)

  1. Pinned note — permanent, always visible, per-exercise. Technique cues. Lives on the Exercise entity.
  2. Session note — free text for this session's performance. Previous session's note shown read-only beneath.
  3. Session-level note — one per workout. Global context (sleep, stress, gym conditions).

3.7 Exercise settings (per-session or permanent)

Accessible from the overflow menu: progression scheme, increment, rep range, warmup rule, rest duration. Editing changes it for this session only by default, with a "save to program" option. A one-off tweak at the rack never silently rewrites your program.

4. Warmup engine

Warmups are suggested, never forced. Every generated row is editable and deletable. Manual warmups can be added on any exercise.

Rule Applies to Ramp
barbell_heavy barbell compounds empty bar × 8, 50% × 5, 75% × 3
compound_machine loaded machines (hack squat, leg press, pulldowns, rows) 50% × 5, 75% × 3
isolation flyes, curls, laterals, extensions single set at ~65% × 8
none bodyweight, accessories —

Percentages are of the target work weight. Results are rounded to the nearest achievable loading given bar weight and plate inventory. If a warmup lands at or below bar weight, it collapses to the empty-bar row. (Plate-math preview shows for kg-mode barbells; it hides when the exercise is displayed in lb.)

Memory beats math: if last session had warmup rows, those are copied forward. "Regenerate warmups" recomputes from the rule.

5. Progression engine

Set per exercise (default: none). The app suggests the next session's prescription; you can always override, and an override becomes the new baseline.

none — no auto-progression

Last session's weights and reps carried forward as-is.

DP — double progression

Target: a rep range (e.g., 6–8) across N sets. All work sets hit the top of the range → next session: weight + increment, reps reset to bottom. Otherwise → same weight, try to add reps.

DDP — dynamic double progression

Same rep range, but sets progress independently. Set 1 hits the top of the range → set 1 gets +increment next time. Set 3 doesn't → set 3 stays. Sets are permanently allowed to run at different weights — they do not re-converge. The UI shows per-set targets.

TP — triple progression (form-gated)

Reserved for heavy technical lifts (squat, bench, deadlift). Same as DP, but a weight increase is only suggested when all work sets in the qualifying session were flagged 👍 (good form). If any set was flagged 👀, the app holds weight and explains why.

RPE gate (applies to all schemes)

If any qualifying work set was logged at RPE ≥ 9.5, the app holds weight and prescribes a repeat, even if the rep target was met. The card shows why. This composes with TP's form gate: a weight increase needs reps met AND all form good AND no RPE ≥ 9.5.

Increment rounding

An increment is never inflated by rounding. If you're at 47.5 kg on a 5 kg stack, +5 means +5, not +7.5. The engine rounds relative to your current weight's offset from the grid.

6. Timers

Rest timer — Per-exercise default duration, editable inline, remembered across sessions. Auto-starts when a set is checked. Presented as an ongoing lock-screen notification with a live OS-rendered countdown that survives a locked screen and even process death; +30s and skip actions live on the notification. An exact-alarm fires a sound at zero from a locked phone. While the app is foregrounded, in-app countdown pips (last 3 seconds) and an optional voice alert ("Rest over" — customizable phrase) take over; the handoff between the two is automatic on lifecycle changes.

Workout timer — Starts on session start, shown in the sticky header and ongoing notification. Elapsed time recorded per session.

Set timer — For timed exercises only. Modal dialog with a 5-second lead-in countdown, work countdown, voice cues ("Get ready" / "Go" / "Time"), and pips at 3/2/1. Can be stopped early.

Idle reminder — If no set has been logged for N minutes (configurable: off / 15 / 30 / 45 / 60), a notification nudges you back.

7. Analytics

Two homes: the per-exercise progress screen (long-press an exercise) and the Analytics hub (drawer → Analytics). PR detection runs for everyone and writes PR rows; the analytics screens and the PR celebration are the paid "observatory." Bodyweight is free.

Per-exercise progress screen:

  • e1RM — Estimated 1RM per work set. Primary formula: RPE-based using an RTS-style reps × RPE → %1RM chart. Fallback: Epley and Brzycki. Best e1RM per session plotted as a line chart.
  • Technique overlay — Sessions that contained a form-flagged ("needs work") set are ringed on the e1RM line, so you can see whether form kept up with the load.
  • RPE-vs-load scatter — Every work set plotted as load × RPE, shaded by recency.
  • Top-set weight — Line chart of heaviest work set per session.
  • Session volume — Bar chart (tonnage = Σ weight × reps).
  • CSV export — The chart's underlying data exported to Downloads.

Analytics hub:

  • Bodyweight trend (free) — Line chart from the optional weigh-in prompted at session finish.
  • Muscle-group volume — Tonnage/hard-set volume grouped by muscle (chest / back / shoulders / arms / legs / core), filterable 30 days / 90 days / all time. Re-categorizing an exercise retroactively corrects past charts; uncategorized exercises are never silently mis-filed.
  • Block-to-block comparison — Pick two blocks; see sessions, calendar span, tonnage, hard sets, and the e1RM change on the lifts they share.

Cross-cutting:

  • PRs — Automatic detection at every finish: heaviest weight and best e1RM per exercise, against all prior finished sessions. A PR triggers a celebration dialog (labels respect the exercise's kg/lb unit).
  • Block report — Per-exercise summary: starting e1RM → current, delta, session count.

Coming in a future update: Garmin FIT export.

8. Training blocks and programs

Block lifecycle: Draft → Active → Completed/Cancelled. One block is active at a time.

Block editor: Ordered list of phases. Each phase = a program for N cycles. Add/remove phases, adjust cycle counts.

Program editor: Reorderable list of days. Each day has a reorderable list of exercise slots. Drag to reorder, swipe to remove, tap to edit slot settings (sets, rep range, progression, increment).

Program snapshots: When a block starts, it takes a private copy of its programs. Edits during a run don't touch the library template, and library edits don't affect running blocks.

Day selection: Shows all days in the active cycle with status (pending / completed / skipped) and staleness ("last done 5 days ago"). Tap to start, skip button to skip. Completing all days closes the cycle automatically.

9. Exercise library

Searchable list of all exercises. Each exercise has: name, equipment type, measurement metric (reps/time), display unit (kg/lb), per-exercise bar weight, plate inventory, loading step, default increment, warmup rule, rest timer default, default progression scheme, pinned note, muscle group, archived flag.

Create new exercises from the library or inline during a session (search for a name, create if not found).

Archive instead of delete if the exercise has logged history — preserves analytics.

10. Session history

All recorded workouts in list or calendar view. Month separators, dots on calendar days. Tap for full detail: every exercise, every set, e1RM calculations, notes. Sessions can be edited (reopens in the session screen), dates changed, or deleted.

Backdating: "Log a past workout" lets you record a session for a previous date. Can be standalone (ad-hoc) or attached to a block's open cycle. The entire session screen works identically but stamps with the chosen date.

11. Backup and data portability

Full database backup as JSON. Auto-backup after every session. Manual backup on demand. Restore from file (validates schema, shows contents preview before overwriting). Export backup to Downloads folder.

The backup format is flat: every database table dumped as an array of row objects. Schema version is included so restores survive app updates — new columns land with defaults, unknown columns are stripped. A backup from any version restores into any other version.

Backups are always free, even in the free tier. Your data is never held hostage.

13. Technical decisions (for anyone building their own)

  • Framework: Flutter (Dart). Android first, iOS later for ~10% extra work.
  • Storage: Local SQLite (sqflite, hand-written SQL). No ORM code generation.
  • State: ChangeNotifier + InheritedWidget. No state management package.
  • Charts: fl_chart.
  • Architecture: domain layer is pure Dart with no Flutter imports — fully unit-testable. Warmup, progression, plate-rounding, and e1RM logic live here and get tests first.
  • Models: Plain immutable Dart classes. No code generation (no freezed, no build_runner).
  • Timers: Ongoing Android notification with an OS-rendered chronometer plus exact-alarm for the end-of-rest sound; wall-clock based (timestamps, not ticks) so elapsed time is correct even if the process is suspended or killed. Notification actions run in a background isolate.
  • Session state: Written to SQLite on every change. A hard kill loses at most the current keystroke.

14. Plate math

Given target weight T, bar weight B, and available plate pairs P: compute per-side loading = (T − B) / 2, greedily fill from largest plate. Default inventory: [25, 20, 15, 10, 5, 2.5, 1.25] → 2.5 kg resolution on a barbell. The UI shows the loading ("2×20 + 1×10 + 1×2.5 per side") under the weight cell for work sets.

15. RPE chart

Standard RTS-style chart mapping reps × RPE → %1RM, covering reps 1–12 and RPE 6.0–10.0 in 0.5 steps. Anchors: 1 rep @ RPE 10 = 100%, 5 reps @ RPE 8 = 81%, 8 reps @ RPE 8 = 71.5%.

e1RM = weight / pct(reps, RPE). When RPE is missing, fall back to Epley: w × (1 + reps/30).
